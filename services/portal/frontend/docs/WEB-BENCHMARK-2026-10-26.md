## 첫 구현 묶음 권고

시민의 **제출 전 확인 + 접수 확인서 + 인쇄**를 먼저 한다. 현재 상세의 ‘접수→배정→처리→완료’는 접수 후 진행 상태이며, 제출 전에 내용을 검토하는 단계와 다르다. 새 확인 단계는 실수를 줄이고 발표에서 서비스가 마무리되는 모습을 보여 준다.

1. 현재 신청 폼의 검증을 통과하면 제목·분야·내용의 검토 화면으로 이동한다. 아직 API로 전송하지 않는다.
2. 수정하면 입력값과 동의를 보존한 폼으로 돌아온다. 뒤로 가기와 이탈 보호도 검증한다.
3. 최종 접수에서 기존 POST를 호출한다. 버튼 중복 클릭을 막고, 실패하면 검토 내용과 재시도 경로를 유지한다.
4. 서버 성공 후 실제 reference와 created_at을 사용해 교육용 접수 확인을 보여 준다. 허구의 처리 기한·담당 부서·통지 발송을 표시하지 않는다.
5. ‘진행 상황 확인’, ‘다른 민원 신청’, ‘접수 확인서 인쇄’를 제공한다. 인쇄에는 필요한 내용과 교육용 표시만 남기고 관리 메뉴를 제외한다.

새로고침/재시도 중 중복 접수 방지의 현재 한계를 별도 점검한다. 브라우저 버튼 잠금만으로 서버 중복 방지를 보장한다고 설명하지 않는다. 실제 PDF 서버 생성이나 알림 발송은 첫 묶음에 필요하지 않다.

### 화면에서 보일 구성

```text
민원 내용 작성
  → 입력 내용 확인  [분야 / 제목 / 내용 / 수정하기]
  → 최종 접수      [서버 결과 대기 / 오류 시 내용 유지]
  → 접수 확인      [실제 접수 번호 / 접수 시각 / 다음 행동]
                    [진행 상황 확인] [접수 확인서 인쇄]
```

완료 기준은 확인 화면 왕복 시 입력 보존, 검토만으로 전송되지 않음, 서버 거절을 성공으로 표시하지 않음, 실제 접수 번호 재조회, 모바일·키보드 확인, 인쇄에 메뉴/버튼이 남지 않음이다. 현재 상태 표시기를 다시 꾸미는 작업과 구분한다.

## 구체적인 아이디어

- **시민의 ‘도와주세요’ 시작점:** ‘도로·교통’처럼 행정 분류를 먼저 아는 사람만 유리하지 않도록, 생활 문제 예시→해당 분야 안내→기존 신청 화면을 연결한다. 기존 6분야 카드와 차별점은 문제로부터 분야를 찾는 과정이다. 안내 예시는 합성 콘텐츠로 제공한다.
- **담당자 답변 도우미:** ‘확인한 내용 / 처리한 내용 / 시민에게 안내할 내용’의 편집 가능한 틀만 제시한다. 기존 답변을 덮어쓰지 않고, 자동으로 완료·전송하지 않는다. 실제 처리 사실을 채워 넣도록 한다.
- **관리자 계정 상세:** 기존 API의 생성 시각·부서·현재 역할·잠금 상태부터 보여 줄 수 있다. 과거 권한 변경 이력은 현재 읽기 API에 없으므로 가짜 기록을 만들지 않는다. 감사 내역은 저장·조회 계약을 마련한 뒤 별도 구현한다.
- **관제의 사건 설명:** 티켓 번호를 눌렀을 때 ‘무슨 일 / 어떤 조치 / 효과 확인 근거 / 원복 근거’를 같은 읽기 순서로 제공한다. 적용 성공과 효과 확인을 합치지 않는다. null/미수신/0건/실패 구분은 유지한다.
- **시연 콘텐츠:** 가상 보행로 조명, 공원 시설, 생활 쓰레기 등 일관된 합성 민원 세트를 별도 미리보기에 준비하면 빈 목록과 ‘테스트’ 제목만 있는 화면보다 업무를 이해하기 쉽다. 사용자가 작성한 현재5005 데이터는 초기화하지 않는다. 합성 티켓의 성과 숫자를 실측 성과로 발표하지 않는다.

## 실제 다른 조 앱을 받으면 볼 기준

첫 화면에서 서비스 목적과 다음 행동이 보이는지, 한 업무가 끝까지 이어지는지, 목록/상세 이동이 편한지, 입력·오류·로딩·완료가 모두 설계됐는지, 모바일·키보드에서 동작하는지, 표시된 숫자가 실제 데이터인지로 비교한다. 같은 조건에서 관찰하고 화면 수나 기술 이름만으로 순위를 정하지 않는다.

현재 권고는 위 공개 사례와 로컬 구현을 바탕으로 한 설계 판단이다. 다른 조 실제 앱의 시각적 장점은 주소·화면을 받은 뒤 추가 비교한다. 새로운 지도/첨부 업로드/AI 챗봇/실시간 알림은 범위를 크게 늘릴 수 있어 첫 묶음 이후에 목적을 정해 검토한다.
