# 해담시청 공통 제약 규칙

규칙 ID: `haedam-rules-2026-10-19-v3`.
원본: `NoBugs-Aleph/aleph-soar-capstone`의 `docs/haedam/PROJECT-RULES.md`.
다른 경로의 동일 파일은 배포용 복사본이며 원본 변경 후 함께 갱신한다.

## 1. 목적과 범위

- 서비스명은 **해담시청 민원포털**이다. 가상 공공기관의 시민 민원·담당자 처리·관리자 업무를 구현한다.
- 프론트 저장소는 `haedam-portal-frontend`, 백엔드는 `haedam-portal-backend`다. 2026-10-19 사용자 결정으로 React + Flask를 사용한다. 포털 프론트·백 구현은 사용자 김명준과 이 Codex 세션이 맡으며 기존 A~D 보안 케이스 책임은 유지한다. 독립 리뷰어는 별도 배정한다.
- 시민: 로그인·민원 작성·본인 민원 조회. 담당자: 권한 있는 민원 조회·상태 처리. 관리자: 승인된 계정 관리·관제 대시보드 링크를 첫 구현 범위로 제안한다. 세부 권한표는 계약 단계에서 확정한다.
- A S1·S4, B S8·S10, C S7, D S12의 필수 4종·케이스 ID 6개와 기존 자리 담당을 유지한다. 10/28 지연 시 S1·S8을 확장으로 전환하는 기존 기준을 따른다. 새로운 통합 스토리라인 시연은 추가하지 않는다.
- 포털·대응 API는 A의 공통 기반이다. 프론트·백엔드 작업자와 리뷰어를 나누는 것은 별도 배정이며 기존 자리 책임을 자동 변경하지 않는다.

## 2. 작업 시작과 협업

- 자기 저장소 `AGENTS.md`, 이 규칙, 담당 작업 카드, 필요한 계약을 읽는다. 구현 전에 파일 범위·연결 담당·관찰 가능한 완료 조건을 기록한다.
- `main`에서 작업 브랜치를 만든다. Codex 브랜치는 `codex/` 접두사를 사용한다. 한 PR에는 검토 가능한 한 가지 변경을 담고 팀원 리뷰 후 병합한다.
- 다른 사람의 수정과 작업 브랜치를 덮어쓰거나 되돌리지 않는다. 공통 파일은 담당을 정하고 충돌을 조율한다.
- 모델·권한·계정의 전역 설정, 다른 저장소와 외부 공유 상태를 작업 중 임의로 바꾸지 않는다.
- 계획·합성 예시·구현·실제 연동·실측 완료를 구분한다. 실행하지 않은 테스트와 연결되지 않은 서비스를 성공으로 표시하지 않는다.

## 3. API·이벤트·사건의 기준

- API·이벤트·사건 계약 원본은 capstone의 `docs/API-CONTRACT.md`와 `contracts/`다. 현재 초안에는 미구현 경로가 있으므로 구현 여부를 확인한다.
- 변경은 `aleph-contract-change` 절차에 따라 원본 문서·스키마·예시·검증과 관련 소비자를 함께 맞춘다. 새 저장소 README에 적용한 원본 커밋을 기록한다.
- 각 저장소는 사용하는 계약만 `contracts/`에 복사하고 출처·커밋을 `contracts/README.md`에 남긴다. 로컬 복사본을 별도 원본으로 발전시키지 않는다.
- 새 민원·인증 API의 경로·메서드·권한·요청·응답·오류·페이지 처리는 원본 계약에 먼저 제안한다. 이 스켈레톤은 새 엔드포인트나 응답 형식을 확정하지 않는다.
- 합성 데이터는 화면 개발에 사용할 수 있으나 개발용 모드임을 명시한다. 실제 연결 실패를 합성 성공 데이터로 바꾸지 않는다. 상태 변경은 서버 응답과 재조회 결과를 반영한다.

## 4. 인증과 데이터 보호

- 인증·역할·민원 소유권·담당 범위를 서버에서 매 요청 검사한다. 화면의 버튼 숨김과 클라이언트가 보낸 역할은 권한 검사가 아니다.
- 비밀번호는 검증된 비밀번호 해시로 저장한다. 비밀번호·세션·토큰·원문 개인정보를 Git, 로그, 증적, 브라우저 저장소에 기록하지 않는다. 브라우저가 DB나 대응 비밀키를 직접 보유하지 않는다.
- 인증 방식·쿠키 속성·세션 만료·CSRF·CORS 정책을 프론트와 백엔드가 함께 정한다. 쿠키 인증을 사용하면 상태 변경 요청의 CSRF 방어를 구현한다. 자격 증명 포함 CORS는 명시한 origin만 허용한다.
- 입력 크기·형식·민원 상태 전이를 검증하고 SQL은 매개변수화한다. 민원 본문 등 사용자 입력은 HTML로 실행되지 않게 출력한다.
- 실제 주민 정보 대신 합성 데이터만 사용한다. 첨부파일은 첫 범위에 포함하지 않으며 추가 시 확장자·크기·저장 경로·접근 권한을 별도로 설계한다.
- 환경값은 비밀값 없는 `.env.example`로 안내하고 실제 값은 Git에서 제외한다. 구현 시 의존성 버전과 잠금 파일, 초기화·마이그레이션 절차를 함께 관리한다.

## 5. 로그·대응·원복

- 구조화 이벤트는 기존 스키마에 맞춘다. 발생 시각·이벤트 ID·출처·출발지·자산·결과를 관찰하고, 익명 요청 등 기존 스키마에 안 맞는 경우 먼저 계약을 보완한다.
- 레포 분리로 요청 경로를 자동 변경하지 않는다. 초기 기준은 기획서의 HTTP 프록시 없는 배치이며, 프론트 빌드 결과를 서비스 VM의 Flask 앱에서 함께 제공하는 안을 검증한다. 실제 경로의 NAT·컨테이너를 포함한 출발지 보존 여부는 실측한다.
- HTTP 프록시가 없는 초기 배치에서는 연결 주소를 출발지로 사용하고 `X-Forwarded-For`를 신뢰하지 않는다. 로그인·접근 로그·차단 검사는 공통 IP 해석 함수를 사용한다. HTTP 프록시 도입 시에는 허용한 접속 경로·전달 헤더 재작성·신뢰할 홉 수·직접 우회 차단을 함께 설계한다.
- S1·S8·S10 인수 전에 공격·정상 출발지 분리, 위조 헤더 무시, 없는 경로의 실제 404와 `web-scan` 이벤트 생성, 앱·Suricata·pfSense 로그의 출발지 연결, 공격 IP 차단 후 정상 사용자 접근 유지를 확인한다. pfSense 로그는 고정한 관측 인터페이스·방향과 본문 출발지 필드로 정규화하며, 모든 연결이 같은 경로를 지난다고 가정하지 않는다.
- 모든 미지정 경로를 프론트 화면의 200 응답으로 바꾸지 않는다. 화면 라우트·정적 자산·API·없는 경로를 구분하고 404 처리 주체가 바뀌면 로그 수집과 탐지 소비자를 함께 맞춘다.
- 브라우저용 API와 n8n용 대응 API는 권한·자격 증명을 구분한다. 관리망·인증된 호출자·허용 대상에 제한하고 공개 프론트에서 대응 API를 직접 호출하지 않는다.
- S1은 출발지 차단이며 계정 잠금을 적용하지 않는다. S4는 계정 잠금과 기존 세션 회수를 함께 검증하고, 비밀번호 재설정 뒤 잠금을 해제한다. 원복으로 회수된 세션을 되살리지 않는다.
- 차단·잠금·복구 요청에는 중복 요청 처리, 사전 상태, 범위·만료, 결과 확인과 실패 기록을 설계한다. 관리망·관제 호출자·복구 경로의 자기 차단을 막고 별도 복구 수단을 둔다.
- 앱 IP 차단과 pfSense 경계 차단을 구분한다. 호출 접수·워크플로 실행·차단 효과·티켓 생성·원복 완료를 각각 실제 결과로 기록한다.
- S7 복구는 승인된 웹 콘텐츠 디렉터리와 검증한 원본만 대상으로 한다. 임의 파일 경로·셸 명령을 외부 요청 그대로 실행하지 않는다.
- Wazuh FIM 감시 경로는 프론트 빌드 산출물의 실제 배포 경로와 맞추고 정상 배포·변조 시험·원복을 구분한다. S12는 정적 화면뿐 아니라 실제 민원 API 응답과 회복도 관찰한다.

## 6. 배치와 자원

- 관제 PC와 공격·서비스 PC 2대 분리, VMnet 내부망, VPN, pfSense의 Suricata, 관제 PC Docker의 보안 대시보드·티켓이라는 합의된 구성을 유지한다. 포털 관리자 메뉴에는 대시보드 링크만 둔다.
- 새 IP 대역·VMnet·외부 노출 포트는 망 담당과 기획서의 허용표에 맞춘다. 프론트·백엔드 저장소 분리가 추가 PC 도입을 뜻하지 않는다.
- 16GB RAM 환경을 고려해 불필요한 상시 서비스와 중복 컨테이너를 늘리지 않는다. 프론트와 백엔드를 각각 빌드·실행한 뒤 통합 자원 사용은 실측한다.
- 실습 배포에서 Flask 개발 서버·디버그 모드를 외부에 노출하지 않는다. 정식 실행 방법은 구현 시 검증 후 README에 적는다.

## 7. 확인과 완료 보고

- 첫 통합은 로그인 → 민원 작성 → 본인 목록 재조회 → 담당자 처리 → 시민의 변경 상태 확인이다. 서버 재시작 후 데이터 유지와 다른 시민의 접근 거부도 확인한다.
- 화면은 로딩·빈 목록·입력 오류·인증 만료·권한 거부·서버 실패·좁은 화면·키보드 조작을 확인한다. 성공 상태를 낙관적으로 고정하지 않는다.
- 필수 케이스마다 공격 → 지정 탐지 경로 → n8n → 차단·인시던트 → 정상 사용자 동작·효과 확인 → 원복을 검증한다. 실제로 사용한 Graylog·Wazuh·Suricata 경로와 미연결 구간을 구분한다.
- 기능 구현 후 필요한 정상·실패·권한·재시도·원복 검증을 수행한다. 문서·빈 폴더만 만든 작업에 기능 구현 완료 표시를 하지 않는다.
- 인수인계에는 변경 파일, 계약 버전, 실행 명령·결과, 실제 연결 상태, 미검증 항목, 다음 담당자의 할 일을 기록한다. 10/23 기획서·11/5 리허설·11/6 본발표 일정을 유지한다.
