`c9f561bac13e08185a5461f79adee937b8cc2b05d225c96cdf16d70b2ae9c962`로 고정한다(11/09 반소람: easyrule 반영 대기 추가. 이전 PR64 검토본은 `f0eea297…53ed`).
대상은 `203.0.113.22` 하나, CE 2.7.2-RELEASE·WAN em0/203.0.113.1이다.

10/28 기준 C #62 포함 통합본 `87997dd` 재빌드와 S1의 실제 저장소 연결·포털 단독
차단/수동 원복은 확인됐다. PF 도구의 대상 `.22`·전용 키/제한 SSH·단독 효과/원복은
여전히 미검증이다. 패키지는 설치 파일 게시 단계만 준비하며 S7 시험과 별도 구간에 적용한다.

## B가 혼자 완료할 수 있는 부분

```powershell
python tools/build_pfsense_bundle.py --out .local/pfsense-response-새버전
python .local/pfsense-response-새버전/install_bundle.py --verify
```

빌더는 새 폴더만 만든다. 도구·출력 계약·설치기·이 안내와 파일별 해시가 들어간다.
기존 출력은 재사용하지 않는다. 마지막 `bundle.json`이 없으면 완료된 패키지가 아니다.
기본 설치기 실행도 파일 검사와 계획만 출력하며 네트워크·장비 설정은 건드리지 않는다.
해시는 전송 오류·버전 혼합 검출용이다. 서명 인증을 대신하지 않으므로 B가 전달한
패키지와 외부 기록의 SHA를 함께 확인한다. 개인키·대응 키·실제 journal은 넣지 않는다.

## 공동시험 시간에 할 B 설치 단계 — 아직 미실행

1. 진행 중 측정/동결과 이전 `.22` 조치 소유권을 확인한다. 포털 단독 112 시험을 먼저 끝낸다.
2. 패키지를 pfSense의 root 전용 임시 디렉터리에 전달하고, `bundle.json`과 파일 해시를 대조한다.
3. pfSense Python3.11로 `install_bundle.py --verify`한다. 사용자 B가 적용 범위를 확인한다.
4. 설치 승인 후 root로 아래 명령을 실행한다.

```sh
/usr/local/bin/python3.11 /B가-확인한-패키지-경로/install_bundle.py --install
```

설치는 `/usr/local/sbin/haedam-pf-response` **한 파일만** root 소유·0750으로 게시한다.
정확한 같은 버전/권한이면 이미 설치됨으로 답하고, 다른 버전·symlink·쓰기 가능한
기존 파일은 거부한다. 교체·삭제·서비스 시작·자동 실행 등록은 하지 않는다.
동시에 다른 파일이 생기면 덮어쓰지 않고 중단한다. SSH 키·pfSense 규칙·journal·
EasyRule·state는 설치기가 변경하거나 생성하지 않는다.

## D 연결 단계 — D와 합의 후 별도 진행

- D 전용 공개키만 B에게 전달한다. B 관리자 개인키를 D에게 주지 않는다.
- 실제 authorized_keys는 기존 관리 키를 보존하고, 장비에서 지원하는 다음 제한을
  확인해 전용 키 줄에만 적용한다. 아래는 **옵션 형식**이며 공개키는 포함하지 않았다.

```text
from="10.250.0.100",restrict,command="/usr/local/sbin/haedam-pf-response"
```

- D→10.250.0.1 TCP22의 리스너·최소 허용·호스트 키 검증을 확인한다.
  포트 추가는 이 패키지가 하지 않는다. 허용되지 않은 IP의 거부도 별도 검증한다.
- 첫 원격 명령은 새 요청 ID의 `haedam-pf-response status 203.0.113.22 REQUEST_ID OWNER_ID`다.
  status도 journal용 디렉터리/lock을 만들 수 있으므로 완전 무기록 읽기라고 부르지 않는다.
- D #72 haedam-14의 파라미터·stdout JSON·실패 처리와 맞춘다. 기본 dry_run을 유지한다.
  `changed:null`, 파싱 실패, 비정상 종료는 성공으로 기록하거나 자동 재시도하지 않는다.
- 실제 B/D 시험은 block → `.22` 새 연결 실패/정상 출발지200 → 같은 요청 재전송 →
  같은 소유자의 새 unblock → `.22`200 복귀다. A 앱 차단과 섞지 않고 결과를 분리한다.
- C/D 소비자는 `bot=112, via=pfsense, action=block` 및 활성 소유권 기준을 맞춘다.
  통합 저장소는 과거 fw_block을 block으로 읽기 호환한다. 새 호출은 이 도구의
  block/unblock을 사용하고 D의 실제 요청 필드/소유자ID/출력 파싱은 게시본에서 별도 대조한다.

## 실패·제거

설치 실패는 자동 재설치하지 않는다. 기존 파일/해시·현재 적용 여부를 읽기 확인한다.
새 도구를 제거하려면 D 호출을 멈추고 도구가 소유한 차단·pending을 먼저 대조한다.
실차단이 남으면 정해진 원복으로 풀고 효과를 검증한다. 도구 파일 삭제는 차단 해제가 아니다.
키 줄 제거·규칙 원복·후보 파일 제거는 생성 범위를 확인한 B가 별도 처리한다.
`/cf/conf/haedam-pf-response` journal이나 기존 키·방화벽·EVE 전송기는 삭제하지 않는다.
