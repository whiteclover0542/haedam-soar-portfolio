# 방식별 검증 체크리스트 (S10 · S8 · S1 · H1)

제어판에서만 동작하는 것으로는 실제 방어가 검증됐다고 보기 어렵습니다. 그래서 같은 케이스를 **제어판을 거치지 않는 경로로도** 공격해, 어느 진입점으로 들어와도 똑같이 **탐지 → 자동 대응 → 차단 → 원복**이 이어지는지 확인합니다.

실제로 **다른 경로는 2개**입니다 — **raw(①, 프로젝트 코드 0)** 와 **프로젝트 스크립트(②)**. ③ 제어판은 `panel.py`가 `run_ticket`을 import해 **②와 똑같은 요청**을 보내므로 "②에 버튼 UI만 씌운 것"입니다. 세 진입점이 모두 같은 실제 백엔드 경로를 돌면, "제어판 전용으로 간략화한 것이 아니라 실제 방어 경로가 검증됐다"는 근거가 됩니다. 리뷰어가 요구한 "제어판 아닌 독립 재현"은 ①(raw)이 가장 강한 증거이고, ③은 "제어판이 가짜 시연이 아니라 진짜 경로를 돈다"를 보여줍니다.

## 결과 기록

- 세 방식 모두 ☑가 되면 그 케이스는 "제어판 단독이 아니라 독립 경로로도 검증됨"이다.
- 방식별로 다른 값이 나오면(예: ①에서만 티켓이 안 생김) 원인을 [실습-안내.md](실습-안내.md)의 "결과가 기대와 다를 때" 표로 확인하고 여기 비고에 적는다.

## 공격 방식 3가지 (진입점)

| # | 방식 | 어떻게 | 실제 경로 |
| --- | --- | --- | --- |
| **①** | 직접 (raw, 코드 없음) | 프로젝트 스크립트 없이 raw `curl`로 포털 API를 직접 호출 | **raw** — 가장 독립적 |
| **②** | 스크립트 CLI | [실습-안내.md](실습-안내.md)의 명령(`s8s10_input.py`·`portal_login.py`) | 프로젝트 스크립트 |
| **③** | 제어판 (= ②의 UI) | `python lab/panel.py` → http://127.0.0.1:8099 버튼. `run_ticket` import → **②와 같은 요청** | 프로젝트 스크립트(②와 동일) |

> 셋 다 **같은 출발지**(.11/.21/.22)에서 나가야 한다. 브라우저로 포털에 직접 로그인해도 서버가 보는 이벤트는 같아 탐지는 동일하지만, 출발지가 호스트 IP가 되고 `localhost:8080`은 pfSense를 우회해 **S10 경계 차단은 재현되지 않는다**. 그래서 세 방식 모두 컨테이너에서 해당 IP로 보낸다.

> **공통 준비:** `python infra/graylog/bootstrap.py --live`로 "mode: live"를 켜 둔다. 같은 출발지는 15분(S1 30분)에 한 번만(탐지 창이 겹치면 회차가 섞임). 기준선·반복 측정은 `python lab/run_ticket.py <CASE> --baseline` / `--restore`로도 돌릴 수 있다.

> **방식 ① 직접 raw로 할 때 함정 3가지** (안 지키면 탐지에 안 걸림)
> - **CSRF 먼저:** 로그인·가입·민원 POST는 쿠키+`X-CSRF-Token`이 있어야 한다. `GET /api/v1/auth/me`로 쿠키와 `csrf_token`을 받아 그 쿠키·토큰으로 POST한다. 없으면 **401이 아니라 403(CSRF_FAILED)** → 안 세어짐. 쿠키는 `-c /tmp/cj.txt -b /tmp/cj.txt`로 컨테이너에 저장되어 `docker exec` 호출 사이에 유지된다.
> - **PowerShell JSON 따옴표:** `docker exec ... curl -d`에 JSON을 넘길 땐 큰따옴표를 `\"`로 escape한다 → `-d '{\"username\":\"u\",\"password\":\"wrong-1\"}'`. 안 하면 따옴표가 벗겨져 본문이 깨지고 **401이 아니라 400(VALIDATION_ERROR)**. (`Invoke-RestMethod`는 cmdlet이라 escape 불필요.)
> - **429 레이트리밋:** 한 출발지에서 5분 안 로그인 **20회**를 넘으면 그 뒤는 `401`이 아니라 `429`가 되고 탐지는 429를 **제외**한다. S1의 9회는 안전하나, 같은 `.11`에서 S1을 5분 내 여러 번 돌리면 뒤 회차가 샌다 → **S1 회차는 5분 이상 간격**.
> - **재사용 전 해제:** 공격 전 그 출발지가 `200`인지 확인(이전 회차 차단이 남아 `000`/`403`이면 먼저 해제).

## 진행 순서 (창 겹침 피하기)

공격 출발지는 3개뿐이다. **같은 출발지만** 탐지 창을 지키면 되고, 다른 출발지는 동시에 진행해도 된다. 그래서 한 케이스를 연속으로 돌리지 말고 출발지를 번갈아 돌려 대기를 겹친다.

| 출발지 | 케이스 | 같은 출발지 재사용 | 비고 |
| --- | --- | --- | --- |
| `.11` | **S1 · H1 공용** | 해제만 하면 바로 다음(대기 ≈0) | 둘 다 매번 다른 계정 → 탐지 키가 달라 섞이지 않음. 단 `.11`은 한 번에 하나씩 |
| `.21` | S8 | **15분** | 출발지 기준 탐지라 창을 지켜야 함 |
| `.22` | S10 | **15분** | 〃 |

**권장 흐름(약 35분):** `.21`·`.22`는 공격 → 1~2분 뒤 효과 확인 → 해제까지 한 번 하고 **15분 타이머**를 건 뒤, 그 사이 `.11`(S1·H1)을 해제만 하며 연달아 돌린다.

```
0분   S10 ①(.22) 공격·효과·해제   →  15분 타이머
2분   S8  ①(.21) 공격·효과·해제   →  15분 타이머
4분   S1  ①(.11) 공격·효과·해제   (계정 새로)
7분   H1  ①(.11) 공격·효과·해제   (계정 새로, .11 해제된 뒤)
10분  S1  ②(.11) / H1 ②(.11) …    (.11 비는 대로 ②③ 계속)
15분  S10 ②(.22) / S8 ②(.21)      (타이머 끝난 소스부터)
…     같은 식으로 ③까지
```

- 매 공격 전 해당 출발지가 이전 회차에서 **해제됐는지**(공격자 `200`) 먼저 확인한다. `000`/`403`이면 먼저 해제.
- `.21`·`.22`는 타이머가 끝나기 전에 같은 소스를 다시 치지 않는다.
- S1·H1은 같은 `.11`이므로 **동시에 두 개를 열어 두지 않는다**(하나 해제 후 다음).

## 체크하는 법

각 케이스 표에서 **점검 항목**마다 세 방식(①②③)으로 각각 해 보고, 기대 결과가 나오면 `☐`를 `☑`로 바꾼다. 기대 결과는 방식과 무관하게 같다(같은 탐지·같은 대응). 제어판에 버튼이 없는 항목(기준선·권한)은 `—`로 두고 `run_ticket.py`로 대신 확인한다.
