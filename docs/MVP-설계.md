## 1. 왜 하는가

팀 프로젝트(해담시청 민원포털 보안 관제·자동 대응)는 PC 4대에 나눠 팀 VPN으로 묶여 있었다.
A 포털 VM, B pfSense·VPN·DB, C Wazuh·티켓 저장소, D Graylog·n8n이 각각 다른 PC에 있었다.
이번 과제는 이것을 **혼자, PC 한 대에서, README만 보고** 처음부터 설치·실행·실측할 수 있는 개인 저장소로 만드는 것이다.
결과물은 개인 포트폴리오(GitHub·PPT·이력서)의 근거가 된다.

진행 방식(사용자 결정): **MVP를 먼저 완주하고, 그 뒤에 일을 하나씩 추가한다.** 문서부터 작성한다.

## 2. 목표 / 비목표 / 실패 조건

**MVP 목표**
1. 개인 저장소 `c:\SR\final_project`에 필요한 코드·설정만 옮기고, 민감정보를 빼서 `.env.example`로 대체한다.
2. 학원 PC 한 대에서 docker compose로 5개 구성(서버, Graylog, Wazuh, pfSense, n8n)이 모두 뜬다.
3. 검사 시연 티켓 **S10(경계 차단·스캔·로그인 반복, 3계층)** 과 **S8(스캔→로그인)** 이 혼자 재현된다.

## 3. 제약

- **학원 PC:** Windows 11, RAM 15.8GB, 디스크 여유 약 81GB, Docker Desktop 설치(WSL2 백엔드), WSL에 Ubuntu·Kali가 있다. 강사 검사도 이 PC에서 한다.
- **WSL2 메모리:** 기본으로 RAM의 50%(약 8GB)만 쓴다. 전체 구성에는 부족하므로 README 1단계에서 `%USERPROFILE%\.wslconfig`에 `memory=12GB`를 설정한다.
- **pfSense는 진짜 pfSense를 쓴다(사용자 결정).** FreeBSD라 공식 컨테이너가 없으므로 QEMU 컨테이너(`qemux/qemu` 계열) 안에서 pfSense CE ISO를 띄운다.
- **n8n의 pfSense 제어는 SSH다**(`haedam-14`의 SSH 노드). 따라서 pfSense VM에 SSH가 열려 있고, n8n 컨테이너에서 닿아야 한다.
- **팀 VPN 주소(10.250.0.x)가 하드코딩돼 있다.** 워크플로·compose·스크립트 곳곳에 있으므로 compose 서비스 이름이나 `.env` 값으로 바꾼다.

## 4. 구성(정해진 것)

### 4-1. 메모리 예산(상한)

| 구성 | 컨테이너 | 상한(대략) | 출처 |
| --- | --- | --- | --- |
| 서버 | 포털 백엔드(Flask)·프론트(React 빌드 정적 서빙)·MySQL·티켓 저장소/대시보드 | 1.2GB | 포털: 김명준 구현, 본인 기여 / 티켓 저장소: 김상혁 |
| Graylog | graylog 6.1·opensearch 2.5·mongo 6 | 4.5GB | 팀 compose(김대훈) 기반 |
| Wazuh | 공식 wazuh-docker single-node(manager·indexer·dashboard) | 3.5GB | 신규 |
| pfSense | QEMU 컨테이너 + pfSense CE VM | 1.2GB | 신규 |
| n8n | n8n 2.39.5 | 0.6GB | 팀 compose(김대훈) 기반 |

합계 약 11GB다. 한 번에 다 못 올리는 경우를 대비해 compose 프로필로 묶음을 끌 수 있게 한다(예: S1만 시험할 때 Wazuh 끄기). 다만 검사에서 "5개 동시 동작"을 보여줄 수 있어야 한다.

### 4-2. 파일 배치

- 최상위 `compose.yaml` 하나가 구성별 compose를 `include`한다.
- 실행 명령: `docker compose up -d` 하나, 또는 `--profile`로 골라 실행

### 4-3. 네트워크

pfSense를 공격 경로 한가운데 둔다.

- **`wan` 네트워크:** 공격 컨테이너와 정상 사용자 컨테이너, pfSense WAN NIC
- **`lan` 네트워크:** 포털, pfSense LAN NIC
- **`soc` 네트워크:** Graylog·Wazuh·n8n·티켓 저장소. 포털과 pfSense 관리 주소도 여기에 연결한다.

동작 원칙은 다음과 같다.

- `wan`의 컨테이너는 pfSense를 게이트웨이로 삼아 포털에 닿는다. pfSense가 출발지 IP를 그대로 넘겨야 포털의 IP 차단과 pfSense 차단이 같은 `src_ip`로 묶인다(NAT 없이 라우팅).
- 공격 컨테이너와 정상 사용자 컨테이너는 서로 다른 고정 IP를 갖는다. 그래야 차단이 공격자만 막고 정상 사용자 200을 유지하는지 보인다. 호스트 브라우저에서 공격하면 출발지가 Docker 게이트웨이로 찍혀 셀프 차단이 되므로 피한다.
- 호스트에 여는 포트는 `127.0.0.1`에만 바인딩한다.
- **대체안(스파이크 실패 시):** QEMU VM에 NIC를 여러 개 붙여 Docker 네트워크에 연결하기 어려우면 pfSense를 `soc`에만 둔다. 공격 컨테이너가 pfSense 자체를 스캔하고(차단 로그 발생), 포털은 직접 공격하는 방식으로 S10 탐지만 재현한다. 이 경우 "pfSense 차단 효과"는 pfSense로 가는 트래픽 차단으로만 보이며, 이 한계를 문제점 기록에 남긴다.

## 5. 먼저 확인할 위험(구축 첫 단계 스파이크)

0. **pfSense VM을 Docker 네트워크 두 개에 연결할 수 있는지:** QEMU VM의 NIC 2개를 각각 `wan`·`lan`에 붙여 라우팅할 수 있는지 확인한다. 안 되면 4-3의 대체안으로 간다.
1. **QEMU 컨테이너의 KVM 사용 여부:** Docker Desktop(WSL2)에서 `/dev/kvm`을 쓸 수 있는지 확인한다. 안 되면 소프트웨어 에뮬레이션(TCG)으로 pfSense 부팅·응답 속도를 재 보고, 쓸 만한지 판단한다. 결과는 문제점 기록에 남긴다.
2. **동시 기동 메모리:** `.wslconfig` 12GB 상태에서 5개 구성을 동시에 올렸을 때 OOM이나 OpenSearch·Wazuh indexer 기동 실패가 없는지 확인한다.
3. **Wazuh indexer:** `vm.max_map_count`와 인증서 생성 단계(wazuh-docker의 generate-certs)가 README 한두 줄로 끝나는지 확인한다.

## 7. 신규 케이스 H1~H4 (MVP 이후)

임계값 N은 정상 사용 기준선을 먼저 잰 뒤 정한다. 기준선과 근거는 티켓 문서에 남긴다.

| ID | 시나리오 | 탐지(Graylog) | 자동 대응(n8n) | 복구 확인 | 포털 변경 |
| --- | --- | --- | --- | --- | --- |
| H1 민원 도배 (가용성) | 매크로로 한 계정이 짧은 시간에 민원을 대량 등록해 담당자 업무를 마비시킴 | 같은 `username`의 `petition.created`가 10분 안에 N건 이상 | 해당 계정의 **민원 작성만 제한**(로그인·조회는 유지) → 티켓 → 알림 | 담당자 해제 후 작성 201, 제한 중 작성 거부(429 또는 403) | 작성 제한 플래그와 대응 API 추가 |
| H2 타인 민원 엿보기 (기밀성) | 시민 계정이 민원 번호를 차례로 넣어 남의 민원(개인정보)을 보려 함 | 같은 `username`·`src_ip`의 민원 상세 조회 거부(403)가 짧은 시간에 N건 이상 | 계정 잠금 + 포털 IP 차단 → 티켓 | 해제 후 본인 민원 조회 200, 타인 민원은 계속 403 | 거부 이벤트(`petition.access_denied`) 추가 |
| H3 민원 처리 결과 조작 (무결성) | 탈취됐거나 악의적인 담당자 계정이 민원 답변·처리 상태를 짧은 시간에 대량 변경(답변 없이 "처리 완료"로 실적 조작) | 같은 staff `username`의 `petition.updated`가 짧은 시간에 N건 이상 | 권한 회수 → 티켓 → 변경 이력 기반으로 **원래 답변·상태 복원** | 변경된 민원이 조작 전 스냅샷과 일치, 관리자 승인 후 역할 복원 | 변경 전 값 기록(이력 테이블)과 복원 API 추가. `petition.updated` 이벤트는 이미 있음 |
| H4 담당자 대량 조회 (기밀성·내부자, 여유 시) | 내부 담당자 계정이 근무 외 시간에 민원 상세를 대량 열람(내부자 유출) | staff 계정의 상세 조회(`petition.viewed`)가 시간당 N건 이상(근무 외 시간 가중) | 역할을 시민 수준으로 **권한 회수** → 티켓 → 관리자 확인 | 관리자 승인으로 역할 복원 후 조회 200 | 조회 이벤트(`petition.viewed`) 추가 |

H3의 복구는 차단 해제가 아니라 데이터 원상 복원이다. 다른 케이스와 다른 장면을 보여준다.

H1에서 계정 전체 대신 "작성 제한"을 쓰는 이유는 민원을 실제로 여러 건 넣는 정상 시민의 업무를 막지 않기 위해서다. 단계적 대응과 그 이유를 PPT의 인상 깊은 부분으로 쓴다.

포털 코드 변경은 본인 기여로 표시한다. 원본 포털 코드는 김명준 작성이다.
