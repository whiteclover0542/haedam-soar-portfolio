## 지표 정의

| 지표 | 정의 |
| --- | --- |
| 자동 대응 | 사람 개입 없이 기대한 차단(S10은 포털+pfSense, S8·S1은 포털)이 모두 적용되고, 공격자 거부(403 또는 연결 실패)와 `normal` 200이 함께 확인된 회차 |
| 원복 | `--restore` 해제 뒤 공격자 요청이 다시 200인 회차 / 원복 시도 |
| 정상 사용자 영향 | 대응 중 `normal`(`203.0.113.100`)의 요청이 200이 아니었던 회차 수 |
| MTTD | Graylog 이벤트의 조건 충족 시각(`event.timestamp`) → 탐지 처리 시각(`timestamp_processing`) |
| 탐지→차단 | 탐지 처리 시각 → 마지막 차단 조치 완료 |
| 입력→차단 | 실행기가 공격 입력을 시작한 시각 → 마지막 차단 조치 완료. Graylog 1분 평가 주기가 포함된 체감 시간 |

중앙값은 자동 대응에 성공한 회차만으로 계산합니다. 실패 회차도 표와 회차 수에는 남깁니다.

- **자동 대응 10/11, 원복 9/11:** 실패는 모두 S10 첫 두 회차다. 1회차는 pfSense 대응 도구가 `easyrule` 반영(약 2초) 전에 결과를 읽어 `outcome_needs_reconciliation`을 냈고, 2회차는 자동 대응은 성공했지만 해제 워크플로가 pfSense 해제 성공(`applied_verified:false`)을 오류로 읽어 멈췄다. 두 곳을 고친 뒤 S10은 3/3, 전체 마지막 9회는 9/9다. 경위는 [S10 티켓](tickets/S10/README.md)과 [작업 일지](journal/2026-11-09.md).
- **정상 사용자 영향 0회:** 11회 모두 대응 중 `normal`(`203.0.113.100`)은 200이었고, S1에서는 공격받은 계정의 주인이 같은 계정으로 정상 로그인(200)했다.
- **MTTD는 팀 값과 직접 비교하지 않는다.** 이 표의 MTTD는 Graylog 이벤트 안의 두 시각(조건 충족→처리) 차이라 0.5초 안팎이다. 팀 리포트의 51.4초는 평가 주기(1분)를 포함한 값으로 보이며, 이 PC에서 같은 성격의 값은 **입력→차단 중앙값 31.0초**(S10 40.0·S8 30.5·S1 18.2초)다. 팀 리포트가 조건 충족 시각을 무엇으로 잡았는지는 이 저장소에서 확인하지 못했다.
- **입력→차단이 팀보다 짧은 이유(추정):** 한 PC 안의 Docker 네트워크라 팀 VPN 왕복이 없고, 포털 로그를 GELF TCP로 보내 유실·재전송이 없다. 남은 지연은 대부분 Graylog의 1분 평가 주기에서 온다(입력 시점에 따라 0~60초). S1이 짧은 것은 실패 로그인 9회를 보내는 동안 이미 주기가 지나가기 때문이다.
- **표본이 작다:** 티켓마다 3~5회라 중앙값은 경향만 보여 준다. 오탐은 아직 기준선 회차가 없어 0/0이다(H1부터 기준선을 잰다).
