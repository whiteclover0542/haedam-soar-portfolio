`lab/run_ticket.py`(H3는 `lab/h3/live.py`)가 자동으로 하는 일을 손으로 한 단계씩 해 봅니다. S7·S12는 탐지 정의·워크플로 반입 전이라 아직 실습할 수 없습니다.

## H2 · 타인 민원 엿보기 (기밀성 · 자동 대응, C · `203.0.113.11`)

H2는 새 공격 시민이 새 피해 시민의 민원 상세를 세 번 조회해 `403`과 `petition.access_denied` 이벤트를 만들고, Graylog → n8n → 티켓 → 포털 IP 차단·공격 계정 잠금 → 사람의 비밀번호 재설정 후 원복까지 확인하는 케이스입니다. 아래 명령은 H1·S1처럼 전체 과정을 실행하고 결과를 `docs/tickets/H2/runs.jsonl`에 남깁니다.

### 1) 준비 및 기존 차단 확인

```powershell
python tools/check_stack.py
python infra/n8n/load.py
python infra/graylog/bootstrap.py --live
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.11 http://203.0.113.1/api/v1/health
```

마지막 값은 공격 전에는 `200`이어야 합니다. `403`이면 이전 실습의 차단이 남은 것이므로 먼저 해당 티켓을 해제합니다.

### 2) H2 전체 실행

```powershell
python lab/run_ticket.py H2 --restore
```

이 명령은 새 피해 시민과 민원 세 건을 만든 뒤, 공격 시민이 타인 민원 상세를 세 번 요청합니다. 입력 결과는 `[403, 403, 403]`, 공격 시민의 자기 민원은 `200`이어야 합니다.

### 3) 탐지·대응 화면 확인

Graylog가 1분 간격으로 5분 창을 평가합니다. 다음 화면에서 같은 실행을 확인합니다.

- **Graylog Search:** `event_type:"petition.access_denied" AND src_ip:203.0.113.11`
- **Graylog Alerts:** `H2 타인 민원 상세 반복 조회 (username+src_ip)`
- **n8n Executions:** `haedam-36 H2`
- **티켓 대시보드:** H2 티켓과 `portal block applied`, `portal lock applied`

### 4) 효과·원복 판정

`run_ticket.py` 결과에서 공격 출발지는 `403`, 다른 출발지에서 시도한 공격 계정 로그인도 `401`, 피해 시민의 자기 민원은 `200`이어야 합니다. `--restore`는 먼저 IP 차단 해제를 요청하지만 계정이 잠긴 동안에는 보류되고, 실습용 새 비밀번호 재설정 뒤 최종 해제를 실행합니다. 결과의 `login_after: 200`, `others_after: 403`, 티켓 상태 `restored`를 확인합니다.

## S10 · 경계 차단 → 스캔 → 로그인 시도 (`203.0.113.22`)

5개 구성(서버·pfSense·Graylog·n8n·티켓 저장소)이 모두 등장해 시연에 가장 좋습니다.

### 1) 공격 전: 공격자도 정상 접속이 되는지

```powershell
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.22 http://203.0.113.1/api/v1/health
```

`200`이 나와야 합니다. `203.0.113.1`은 pfSense의 WAN 주소이고, pfSense가 80번을 포털(`10.250.0.2:5000`)로 넘겨 줍니다.

### 2) 공격 ① 경계에서 막히는 신호: ping

```powershell
docker exec haedam-attacker ping -I 203.0.113.22 -c 1 -W 1 203.0.113.1
```

응답이 없어야 정상입니다(100% packet loss). pfSense가 WAN으로 들어온 ping을 기본 규칙으로 막고 그 기록을 Graylog로 보냅니다.

- **pfSense:** Status → System Logs → Firewall에 `203.0.113.22` 차단(빨간 X) 한 줄
- **Graylog Search:** `rule:"pfsense-block" AND src_ip:203.0.113.22`

### 3) 공격 ② 포털 스캔과 로그인 시도

입력 도구(원작 B)가 요청 3개를 보냅니다: 없는 경로 스캔(404) → 로그인 화면용 보안 토큰 받기(200) → 틀린 비밀번호로 로그인(401).

```powershell
docker cp tools/s8s10_input.py haedam-attacker:/lab/s8s10_input.py
$run = "manual" + (Get-Date -Format "HHmmss")
docker exec haedam-attacker python /lab/s8s10_input.py --case S10 --run-id $run --out /tmp/$run.json --execute
docker exec haedam-attacker cat /tmp/$run.json
```

출력의 `"http"`에서 `status`가 `404`, `200`, `401` 순서인지 봅니다(`ping`도 한 번 더 보냄).

- **Graylog Search:** `src_ip:203.0.113.22` → `web-scan`(404), `login-bruteforce`(401) 이벤트

### 4) 탐지와 대응 (최대 1~2분 기다림)

Graylog는 1분마다 "15분 안에 같은 출발지에서 경계 차단·스캔·로그인 실패가 모두 나왔는가"를 확인합니다.

- **Graylog → Alerts:** `S10 경계 차단·스캔·로그인 반복`(같은 입력이 S8 조건도 채워 S8 이벤트도 함께 뜰 수 있음)
- **n8n → Executions:** `haedam-32 S8·S10 …` 실행 → 열어 보면 포털 차단(`haedam-12`)·pfSense 차단(`haedam-14`)·티켓 기록(`haedam-10`) 노드가 초록색
- **티켓 대시보드:** 새 티켓, 조치 `portal block applied`와 `pfsense block applied`
- **pfSense → Diagnostics → Tables → `EasyRuleBlockHostsWAN`:** `203.0.113.22`

### 5) 효과 확인

```powershell
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --max-time 5 --interface 203.0.113.22 http://203.0.113.1/api/v1/health
docker exec haedam-normal   curl -s -o /dev/null -w "%{http_code}`n" --max-time 5 http://203.0.113.1/api/v1/health
```

| 누구 | 기대 | 뜻 |
| --- | --- | --- |
| 공격자 `.22` | `000` | pfSense에서 연결 자체가 막힘(포털까지 가지도 못함) |
| 정상 시민 `.100` | `200` | 다른 사람은 그대로 이용 가능 |

### 6) 해제(원복) — 사람이 확인한 뒤

```powershell
$body = '{"seat":"B","case_id":"S8","group_key":"203.0.113.22","approver":"운영자","dry_run":false,"reason":"실습 원복"}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5678/webhook/haedam-release -ContentType 'application/json' -Headers @{ 'X-Haedam-Key' = $env:N8N_WEBHOOK_KEY } -Body $body
```

- `case_id`는 티켓 대시보드에 보이는 그 티켓의 값을 씁니다(S10 입력은 보통 `S8` 티켓 하나로 묶임).
- 응답의 `steps`가 `1 released`(pfSense) → `2 released`(포털) 순서면 성공입니다. 경계를 먼저 풀고 앱을 풉니다.
- 1)의 명령을 다시 쳐서 공격자가 `200`으로 돌아왔는지, 티켓이 `restored`인지 확인합니다.

## S4 · 실패 뒤 성공 → 계정 잠금 (`203.0.113.11`, 본인 티켓)

S1이 "틀린 비밀번호를 계속 넣는" 공격이라면, S4는 **결국 맞힌** 경우입니다. 이미 로그인에 성공했으니 출발지를 막아도 늦습니다. 그래서 계정을 잠그고 그 계정의 세션을 모두 끊습니다.

### 1) 계정 주인 가입, 공격자가 실패 5번 뒤 성공

```powershell
$user = "zz_a_s4_" + (Get-Date -Format "HHmmss")
$env:PW = "Practice-" + (Get-Random)            # 계정 주인의 비밀번호(공격자도 알고 있다고 가정)
docker cp lab/portal_login.py haedam-normal:/lab/portal_login.py
docker cp lab/portal_login.py haedam-attacker:/lab/portal_login.py
docker exec -e PW haedam-normal python /lab/portal_login.py --source 203.0.113.100 register $user                 # statuses [201]
docker exec -e PW haedam-attacker python /lab/portal_login.py --source 203.0.113.11 takeover $user 5 --hold 180   # 401×5, 200, 세션이 끊길 때까지 대기
```

마지막 명령은 로그인에 성공한 세션을 쥐고 3초마다 로그인이 필요한 화면을 다시 엽니다. 출력의 `session`이 `[200, 401]`이고 `revoked_after_s`가 찍히면 그 세션이 회수된 것입니다(보통 30~60초). 출력의 `user_id`는 원복에 씁니다.

Graylog 정의: 10분 안에 같은 `username`·`src_ip`에서 로그인 실패와 성공이 모두 있고 합계 6건 이상이면 탐지합니다.

### 2) 효과

```powershell
docker exec -e PW haedam-attacker python /lab/portal_login.py --source 203.0.113.11 login $user    # statuses [401] — 맞는 비밀번호도 거부
docker exec haedam-normal curl -s -o /dev/null -w "%{http_code}`n" http://203.0.113.1/api/v1/health   # 200 — 다른 시민은 그대로
```

볼 곳: Graylog Alerts의 `S4 실패 뒤 성공 (username+src_ip)`, n8n Executions의 `haedam-31`·`haedam-13`, 티켓 대시보드의 S4 티켓(조치 `portal lock → applied`).

### 3) 원복: 비밀번호 재설정 (담당자가 계정 주인을 확인한 뒤)

```powershell
$env:K = (Select-String '^PORTAL_RESPONSE_KEY=' .env).Line.Split('=',2)[1]
$env:U = "<1)의 user_id>"; $env:I = "manual-reset-$user"; $env:NP = "Practice-" + (Get-Random)
docker exec -e K -e U -e I -e NP haedam-n8n node -e "fetch('http://10.250.0.2:5000/api/v1/response/accounts/'+process.env.U+'/reset',{method:'POST',headers:{'X-Response-Key':process.env.K,'Idempotency-Key':process.env.I,'Content-Type':'application/json'},body:JSON.stringify({new_password:process.env.NP})}).then(r=>console.log(r.status))"   # 200
$body = '{"seat":"A","case_id":"S4","group_key":"' + $user + '","approver":"운영자","dry_run":false,"reason":"실습 원복"}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5678/webhook/haedam-release -ContentType 'application/json' -Headers @{ 'X-Haedam-Key' = $env:N8N_WEBHOOK_KEY } -Body $body   # verdict released, 티켓 restored
$env:PW = $env:NP
docker exec -e PW haedam-normal python /lab/portal_login.py --source 203.0.113.100 login $user     # statuses [200]
```

공격자가 알던 옛 비밀번호는 재설정 뒤에도 `401`입니다. 같은 출발지에서 다시 하려면 **5분** 기다립니다(포털이 출발지마다 5분에 로그인 20번까지만 받음).

Graylog 정의: 10분 안에 같은 `username`의 민원 등록(`petition.created`)이 5건 이상이면 탐지합니다. 출발지가 아니라 **계정**으로 셉니다.

### 2) 1~2분 뒤 효과


볼 곳: Graylog Alerts의 "H1 민원 도배 (username)", n8n Executions의 `haedam-35`·`haedam-18`, 티켓 대시보드의 H1 티켓(조치 `portal restrict_posting → applied`).

### 3) 해제 (담당자가 확인 후)

H1은 `haedam-50`이 아니라 포털 대응 API로 직접 풉니다. 대응 API는 내부망에서만 열려 있어 n8n 컨테이너를 거쳐 부릅니다.


## H3 · 민원 처리 결과 조작 (무결성 · 자동 대응, C · 담당자 계정)

H3는 출발지가 아니라 **담당자 계정**으로 셉니다. 탈취된 담당자 계정이 민원 처리 결과를 짧은 시간에 여러 건 바꾸는 상황입니다. 포털은 민원 상태를 바꿀 때마다 변경 전 값(상태·답변·담당자)을 스냅샷으로 남깁니다.

### 1) 전체 실행

```powershell
python tools/check_stack.py
python infra/n8n/load.py
python infra/graylog/bootstrap.py --live
python lab/h3/live.py
```

이 명령은 회차마다 새 `zz_h3_staff_…` 담당자와 `zz_h3_owner_…` 신청자를 관리자 계정으로 만듭니다. 신청자가 민원 3건을 내고, 담당자가 세 건을 연달아 `received` → `in_progress`로 바꿉니다(`petition.updated` 3건). 결과는 `docs/tickets/H3/runs.jsonl`에 남고, 화면에는 `{"result": "pass"}` 한 줄이 나옵니다. 비밀번호·쿠키는 출력하지 않습니다.

### 2) 탐지·대응 화면 확인

Graylog는 1분마다 5분 창을 보고, 같은 `username`의 `petition.updated`가 3건 이상이면 경보를 냅니다. 집계 경보에는 `petition_id`가 남지 않으므로 n8n은 담당자 이름만 넘기고, 포털이 그 담당자가 최근 15분 안에 바꾼 민원을 모두 찾아 민원별 가장 이른 스냅샷으로 되돌립니다.

- **Graylog Search:** `event_type:"petition.updated" AND username:zz_h3_staff_*`
- **Graylog Alerts:** `H3 staff petition updates`
- **n8n Executions:** `haedam-37 H3 petition snapshot restore`(티켓 → 계정 잠금 → 스냅샷 복원 → Discord)
- **티켓 대시보드:** H3 티켓과 `portal lock applied`

### 3) 효과·원복 판정

| 확인 | 기대 | 뜻 |
| --- | --- | --- |
| 신청자의 민원 3건 상세 | `200`, 모두 `received` | 바뀐 처리 결과가 변경 전으로 돌아옴, 신청자는 계속 이용 |
| 잠긴 담당자 로그인 | `401` | 탈취 계정의 추가 조작 차단(세션도 회수) |
| 관리자 해제 뒤 담당자 로그인 | `200` | 사람이 오탐 여부를 확인하고 푸는 원복 |

`live.py`는 세 조건과 티켓의 `lock` 조치가 모두 확인돼야 `pass`로 기록합니다. 실패하면 남은 잠금을 관리자 해제로 정리합니다. 손으로 풀 때는 관리자 화면(http://127.0.0.1:8080)의 사용자 관리에서 해당 `zz_h3_staff_…` 계정을 잠금 해제합니다.

## 결과가 기대와 다를 때

| 증상 | 확인 |
| --- | --- |
| 2분이 지나도 티켓이 없음 | `bootstrap.py --live`를 실행했는지(`mode: live`). Graylog Alerts에 이벤트가 있는지 → 없으면 Search에서 해당 `src_ip` 로그가 들어왔는지 |

| n8n 실행은 있는데 티켓이 없음 | 실행의 마지막 노드가 `저장 실패 응답`이면 티켓 저장소가 기록을 거부한 것. `docker logs haedam-ticket-store`에서 `POST /api/v1/tickets/record` 400 확인 |

같은 일을 반복 측정할 때는 `python lab/run_ticket.py S10 --restore`가 위 1)~6)을 한 번에 하고 결과를 `docs/tickets/S10/runs.jsonl`에 남깁니다.
