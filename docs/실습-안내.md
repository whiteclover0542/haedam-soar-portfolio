# 직접 해 보는 실습 안내 (S10 · S8 · S1)

`lab/run_ticket.py`가 자동으로 하는 일을 손으로 한 단계씩 해 봅니다.

> **버튼으로 하려면:** `python lab/panel.py` → http://127.0.0.1:8099 실습 제어판. 티켓마다 [공격]·[효과 확인]·[해제] 버튼이 아래 명령을 그대로 실행하고, 실행한 명령과 결과를 화면 로그에 남깁니다. 티켓 상태·조치는 5초마다 갱신됩니다. 0. 준비(`bootstrap.py --live`)는 먼저 해 둡니다. 명령은 프로젝트 폴더에서 **PowerShell**로 칩니다. 공격 명령은 모두 `haedam-attacker` 컨테이너 안에서 실행되므로 이 PC 밖으로는 나가지 않습니다.

## 0. 준비 (한 번)

```powershell
python tools/check_stack.py                       # 6개 모두 OK인지
$env:GRAYLOG_ADMIN_PASSWORD = (Select-String '^GRAYLOG_ADMIN_PASSWORD=' .env).Line.Split('=',2)[1]

```

브라우저 탭을 미리 열어 둡니다.

| 탭 | 주소 | 볼 것 |
| --- | --- | --- |
| Graylog | http://127.0.0.1:9000 (admin / `.env`의 `GRAYLOG_ADMIN_PASSWORD`) | Search, Alerts |
| n8n | http://127.0.0.1:5678 | Executions(실행 기록) |
| 티켓 대시보드 | http://127.0.0.1:8089 | 새 티켓과 조치 |
| pfSense | https://127.0.0.1:8443 | Diagnostics → Tables, Status → System Logs → Firewall |

> **같은 출발지는 15분(S1은 30분)에 한 번만.** Graylog가 같은 출발지의 로그를 15분 창으로 묶어 세므로, 연달아 공격하면 앞 회차 로그와 섞여 결과가 틀어집니다. 다시 하고 싶으면 기다리거나 다른 티켓(다른 출발지)을 합니다.

## S10 · 경계 차단 → 스캔 → 로그인 시도 (`203.0.113.22`)

5개 구성(서버·pfSense·Graylog·n8n·티켓 저장소)이 모두 등장해 시연에 가장 좋습니다.

### 1) 공격 전: 공격자도 정상 접속이 되는지

```powershell
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.22 http://203.0.113.1/api/v1/health
```

`200`이 나와야 합니다. `203.0.113.1`은 pfSense의 WAN 주소이고, pfSense가 80번을 포털(`10.250.0.2:5000`)로 넘겨 줍니다.

### 2) 공격 ① 경계에서 막히는 신호: ping

```powershell
docker exec haedam-attacker ping -I 203.0.113.22 -c 1 -W 1 203.0.113.1
```

응답이 없어야 정상입니다(100% packet loss). pfSense가 WAN으로 들어온 ping을 기본 규칙으로 막고 그 기록을 Graylog로 보냅니다.

- **pfSense:** Status → System Logs → Firewall에 `203.0.113.22` 차단(빨간 X) 한 줄
- **Graylog Search:** `rule:"pfsense-block" AND src_ip:203.0.113.22`

### 3) 공격 ② 포털 스캔과 로그인 시도

입력 도구(원작 김명준)가 요청 3개를 보냅니다: 없는 경로 스캔(404) → 로그인 화면용 보안 토큰 받기(200) → 틀린 비밀번호로 로그인(401).

```powershell
docker cp tools/s8s10_input.py haedam-attacker:/lab/s8s10_input.py
$run = "manual" + (Get-Date -Format "HHmmss")
docker exec haedam-attacker python /lab/s8s10_input.py --case S10 --run-id $run --out /tmp/$run.json --execute
docker exec haedam-attacker cat /tmp/$run.json
```

출력의 `"http"`에서 `status`가 `404`, `200`, `401` 순서인지 봅니다(`ping`도 한 번 더 보냄).

- **Graylog Search:** `src_ip:203.0.113.22` → `web-scan`(404), `login-bruteforce`(401) 이벤트

### 4) 탐지와 대응 (최대 1~2분 기다림)

Graylog는 1분마다 "15분 안에 같은 출발지에서 경계 차단·스캔·로그인 실패가 모두 나왔는가"를 확인합니다.

- **Graylog → Alerts:** `S10 경계 차단·스캔·로그인 반복`(같은 입력이 S8 조건도 채워 S8 이벤트도 함께 뜰 수 있음)
- **n8n → Executions:** `haedam-32 S8·S10 …` 실행 → 열어 보면 포털 차단(`haedam-12`)·pfSense 차단(`haedam-14`)·티켓 기록(`haedam-10`) 노드가 초록색
- **티켓 대시보드:** 새 티켓, 조치 `portal block applied`와 `pfsense block applied`
- **pfSense → Diagnostics → Tables → `EasyRuleBlockHostsWAN`:** `203.0.113.22`

### 5) 효과 확인

```powershell
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --max-time 5 --interface 203.0.113.22 http://203.0.113.1/api/v1/health
docker exec haedam-normal   curl -s -o /dev/null -w "%{http_code}`n" --max-time 5 http://203.0.113.1/api/v1/health
```

| 누구 | 기대 | 뜻 |
| --- | --- | --- |
| 공격자 `.22` | `000` | pfSense에서 연결 자체가 막힘(포털까지 가지도 못함) |
| 정상 시민 `.100` | `200` | 다른 사람은 그대로 이용 가능 |

### 6) 해제(원복) — 사람이 확인한 뒤

```powershell
$body = '{"seat":"B","case_id":"S8","group_key":"203.0.113.22","approver":"반소람","dry_run":false,"reason":"실습 원복"}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5678/webhook/haedam-release -ContentType 'application/json' -Headers @{ 'X-Haedam-Key' = $env:N8N_WEBHOOK_KEY } -Body $body
```

- `case_id`는 티켓 대시보드에 보이는 그 티켓의 값을 씁니다(S10 입력은 보통 `S8` 티켓 하나로 묶임).
- 응답의 `steps`가 `1 released`(pfSense) → `2 released`(포털) 순서면 성공입니다. 경계를 먼저 풀고 앱을 풉니다.
- 1)의 명령을 다시 쳐서 공격자가 `200`으로 돌아왔는지, 티켓이 `restored`인지 확인합니다.

## S8 · 포털 스캔 → 로그인 시도 (`203.0.113.21`)

S10과 같은 입력에서 **ping만 빠진** 경우입니다. 경계 신호가 없으니 pfSense는 건드리지 않고 포털에서만 막습니다.

```powershell
$run = "manual" + (Get-Date -Format "HHmmss")
docker exec haedam-attacker python /lab/s8s10_input.py --case S8 --run-id $run --out /tmp/$run.json --execute
```

1~2분 뒤:

```powershell
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.21 http://203.0.113.1/api/v1/health   # 403
docker exec haedam-normal   curl -s -o /dev/null -w "%{http_code}`n" http://203.0.113.1/api/v1/health                          # 200
```

- 공격자는 `000`이 아니라 **`403`**: 연결은 pfSense를 통과하고, 포털이 `IP_BLOCKED`로 거절합니다.
- 티켓 조치에 `pfsense`가 없어야 합니다.
- 해제: S10 6)과 같고 `group_key`만 `203.0.113.21`.

## S1 · 로그인 무차별 대입 (`203.0.113.11`, 본인 티켓)

### 1) 피해자 계정 만들기 (정상 시민이 가입)

```powershell
$user = "zz_a_s1_" + (Get-Date -Format "HHmmss")
$env:PW = "Practice-" + (Get-Random)            # 이 창에서만 쓰는 임시 비밀번호
docker cp lab/portal_login.py haedam-normal:/lab/portal_login.py
docker cp lab/portal_login.py haedam-attacker:/lab/portal_login.py
docker exec -e PW haedam-normal python /lab/portal_login.py --source 203.0.113.100 register $user     # statuses [201]
```

### 2) 공격: 같은 계정에 틀린 비밀번호 9번

```powershell
docker exec haedam-attacker python /lab/portal_login.py --source 203.0.113.11 fail $user 9           # statuses 401 ×9
```

Graylog 정의: 30분 안에 같은 `username`+`src_ip`의 401이 8번을 넘으면 탐지합니다.

### 3) 1~2분 뒤 효과

```powershell
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.11 http://203.0.113.1/api/v1/health   # 403
docker exec -e PW haedam-normal python /lab/portal_login.py --source 203.0.113.100 login $user                         # statuses [200]
```

**계정이 아니라 출발지를 막았기 때문에** 계정 주인은 같은 계정으로 정상 로그인할 수 있습니다. 공격받았다고 피해자 계정까지 잠그면 피해자가 두 번 피해를 봅니다.

해제: S10 6)에서 `"seat":"A","case_id":"S1","group_key":"<$user 값>"`.

## 결과가 기대와 다를 때

| 증상 | 확인 |
| --- | --- |
| 2분이 지나도 티켓이 없음 | `bootstrap.py --live`를 실행했는지(`mode: live`). Graylog Alerts에 이벤트가 있는지 → 없으면 Search에서 해당 `src_ip` 로그가 들어왔는지 |
| Alerts는 있는데 n8n 실행이 없음 | n8n Executions에 실패 기록이 있는지, `python infra/n8n/load.py`를 다시 실행 |
| 공격자가 처음부터 403/000 | 앞 회차 차단이 남아 있음 → 6)의 해제를 먼저 |
| 티켓 조치가 `dry_run` | Graylog 알림이 관찰 모드 → `bootstrap.py --live` |

같은 일을 반복 측정할 때는 `python lab/run_ticket.py S10 --restore`가 위 1)~6)을 한 번에 하고 결과를 `docs/tickets/S10/runs.jsonl`에 남깁니다.
