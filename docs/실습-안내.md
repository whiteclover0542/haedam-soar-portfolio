## H1 · 민원 도배 (`203.0.113.14`, 본인 티켓)

### 1) 공격: 계정을 만들어 민원 8건 연달아 등록

```powershell
$user = "zz_a_h1_" + (Get-Date -Format "HHmmss")
$env:PW = "Practice-" + (Get-Random)            # 이 창에서만 쓰는 임시 비밀번호
docker cp lab/portal_login.py haedam-attacker:/lab/portal_login.py
docker cp lab/portal_login.py haedam-normal:/lab/portal_login.py
docker exec -e PW haedam-attacker python /lab/portal_login.py --source 203.0.113.14 register $user   # statuses [201]
docker exec -e PW haedam-attacker python /lab/portal_login.py --source 203.0.113.14 post $user 8     # statuses 201 ×8
```

Graylog 정의: 10분 안에 같은 `username`의 민원 등록(`petition.created`)이 5건 이상이면 탐지합니다. 출발지가 아니라 **계정**으로 셉니다.

### 2) 1~2분 뒤 효과

```powershell
docker exec -e PW haedam-attacker python /lab/portal_login.py --source 203.0.113.14 post $user 1     # statuses [429], login 200, list 200
$other = "zz_a_h1n_" + (Get-Date -Format "HHmmss")
docker exec -e PW haedam-normal python /lab/portal_login.py --source 203.0.113.100 register $other   # 다른 정상 시민
docker exec -e PW haedam-normal python /lab/portal_login.py --source 203.0.113.100 post $other 1     # statuses [201]
```

**그 계정의 민원 작성만 막았기 때문에** 같은 계정으로 로그인하고 자기 민원을 조회하는 것은 그대로 되고, 다른 시민은 계속 민원을 낼 수 있습니다. IP를 막으면 같은 공유기·기관망을 쓰는 시민까지 막힙니다.

볼 곳: Graylog Alerts의 "H1 민원 도배 (username)", n8n Executions의 `haedam-35`·`haedam-18`, 티켓 대시보드의 H1 티켓(조치 `portal restrict_posting → applied`).

### 3) 해제 (담당자가 확인 후)

다른 케이스와 같은 해제 웹훅(`haedam-50`)을 씁니다. 티켓에 `restrict_posting`이 있으면 웹훅이 작성 제한 해제 분기로 가서 제한을 풀고, 티켓을 `restored`로 바꾸고, Discord 원복 카드를 보냅니다. `group_key`는 출발지가 아니라 **계정 이름**입니다.

```powershell
$body = '{"seat":"A","case_id":"H1","group_key":"' + $user + '","approver":"운영자","dry_run":false,"reason":"실습 원복"}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5678/webhook/haedam-release -ContentType 'application/json' -Headers @{ 'X-Haedam-Key' = $env:N8N_WEBHOOK_KEY } -Body $body   # verdict released
docker exec -e PW haedam-attacker python /lab/portal_login.py --source 203.0.113.14 post $user 1     # statuses [201]
```

응답이 `verdict: released`, 티켓이 `restored`면 성공입니다. 티켓은 대시보드에서 메모를 남기고 닫습니다. 포털 대응 API(`/api/v1/response/accounts/posting`)로 직접 풀어도 제한은 풀리지만, 티켓이 `대응 중`에 남고 원복 알림도 오지 않으니 쓰지 않습니다.

## H2 · 타인 민원 엿보기 (기밀성 · 자동 대응, C · `203.0.113.15`)

H2는 새 공격 시민이 새 피해 시민의 민원 상세를 세 번 조회해 `403`과 `petition.access_denied` 이벤트를 만들고, Graylog → n8n → 티켓 → 포털 IP 차단·공격 계정 잠금 → 사람의 비밀번호 재설정 후 원복까지 확인하는 케이스입니다. 아래 명령은 H1·S1처럼 전체 과정을 실행하고 결과를 `docs/tickets/H2/runs.jsonl`에 남깁니다.

### 1) 준비 및 기존 차단 확인

```powershell
python tools/check_stack.py
python infra/n8n/load.py
python infra/graylog/bootstrap.py --live
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.15 http://203.0.113.1/api/v1/health
```

마지막 값은 공격 전에는 `200`이어야 합니다. `403`이면 이전 실습의 차단이 남은 것이므로 먼저 해당 티켓을 해제합니다.

### 2) H2 전체 실행

```powershell
python lab/run_ticket.py H2 --restore
```

이 명령은 새 피해 시민과 민원 세 건을 만든 뒤, 공격 시민이 타인 민원 상세를 세 번 요청합니다. 입력 결과는 `[403, 403, 403]`, 공격 시민의 자기 민원은 `200`이어야 합니다.

### 3) 탐지·대응 화면 확인

Graylog가 1분 간격으로 5분 창을 평가합니다. 다음 화면에서 같은 실행을 확인합니다.

- **Graylog Search:** `event_type:"petition.access_denied" AND src_ip:203.0.113.15`
- **Graylog Alerts:** `H2 타인 민원 상세 반복 조회 (username+src_ip)`
- **n8n Executions:** `haedam-36 H2`
- **티켓 대시보드:** H2 티켓과 `portal block applied`, `portal lock applied`

### 4) 효과·원복 판정

`run_ticket.py` 결과에서 공격 출발지는 `403`, 다른 출발지에서 시도한 공격 계정 로그인도 `401`, 피해 시민의 자기 민원은 `200`이어야 합니다. `--restore`는 먼저 IP 차단 해제를 요청하지만 계정이 잠긴 동안에는 보류되고, 실습용 새 비밀번호 재설정 뒤 최종 해제를 실행합니다. 결과의 `login_after: 200`, `others_after: 403`, 티켓 상태 `restored`를 확인합니다.

## H3 · 민원 처리 결과 조작 (무결성 · 자동 대응, C · 담당자 계정)

H3는 출발지가 아니라 **담당자 계정**으로 셉니다. 탈취된 담당자 계정이 민원 처리 결과를 짧은 시간에 여러 건 바꾸는 상황입니다. 포털은 민원 상태를 바꿀 때마다 변경 전 값(상태·답변·담당자)을 스냅샷으로 남깁니다.

### 1) 전체 실행

```powershell
python tools/check_stack.py
python infra/n8n/load.py
python infra/graylog/bootstrap.py --live
python lab/h3/live.py
```

이 명령은 회차마다 새 `zz_h3_staff_…` 담당자와 `zz_h3_owner_…` 신청자를 관리자 계정으로 만듭니다. 신청자가 민원 3건을 내고, 담당자가 세 건을 연달아 `received` → `in_progress`로 바꿉니다(`petition.updated` 3건). 결과는 `docs/tickets/H3/runs.jsonl`에 남고, 화면에는 `{"result": "pass"}` 한 줄이 나옵니다. 비밀번호·쿠키는 출력하지 않습니다.

### 2) 탐지·대응 화면 확인

Graylog는 1분마다 5분 창을 보고, 같은 `username`의 `petition.updated`가 3건 이상이면 경보를 냅니다. 집계 경보에는 `petition_id`가 남지 않으므로 n8n은 담당자 이름만 넘기고, 포털이 그 담당자가 최근 15분 안에 바꾼 민원을 모두 찾아 민원별 가장 이른 스냅샷으로 되돌립니다.

- **Graylog Search:** `event_type:"petition.updated" AND username:zz_h3_staff_*`
- **Graylog Alerts:** `H3 staff petition updates`
- **n8n Executions:** `haedam-37 H3 petition snapshot restore`(티켓 → 계정 잠금 → 스냅샷 복원 → Discord)
- **티켓 대시보드:** H3 티켓과 `portal lock applied`

### 3) 효과·원복 판정

| 확인 | 기대 | 뜻 |
| --- | --- | --- |
| 신청자의 민원 3건 상세 | `200`, 모두 `received` | 바뀐 처리 결과가 변경 전으로 돌아옴, 신청자는 계속 이용 |
| 잠긴 담당자 로그인 | `401` | 탈취 계정의 추가 조작 차단(세션도 회수) |
| 관리자 해제 뒤 담당자 로그인 | `200` | 사람이 오탐 여부를 확인하고 푸는 원복 |

`live.py`는 세 조건과 티켓의 `lock` 조치가 모두 확인돼야 `pass`로 기록합니다. 실패하면 남은 잠금을 관리자 해제로 정리합니다.

손으로 풀 때는 두 단계입니다. 관리자 화면(http://127.0.0.1:8080)의 사용자 관리에서 해당 `zz_h3_staff_…` 계정의 잠금을 먼저 풉니다. 그다음 해제 웹훅을 부르면 `haedam-50`이 계정이 풀린 것을 확인하고 티켓을 `restored`로 바꿉니다. 잠금을 풀기 전에 부르면 `held_still_locked`로 보류됩니다.

```powershell
$body = '{"seat":"C","case_id":"H3","group_key":"zz_h3_staff_…","approver":"운영자","dry_run":false,"reason":"오탐 확인 후 원복"}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5678/webhook/haedam-release -ContentType 'application/json' -Headers @{ 'X-Haedam-Key' = $env:N8N_WEBHOOK_KEY } -Body $body   # verdict released
```

## S4 · 실패 뒤 성공 → 계정 잠금 (`203.0.113.13`, 본인 티켓)

$user = "zz_a_s4_" + (Get-Date -Format "HHmmss")
$env:PW = "Practice-" + (Get-Random)            # 계정 주인의 비밀번호(공격자도 알고 있다고 가정)

## S10 · 경계 차단 → 스캔 → 로그인 시도 (`203.0.113.22`)

5개 구성(서버·pfSense·Graylog·n8n·티켓 저장소)이 모두 등장해 시연에 가장 좋습니다.

### 1) 공격 전: 공격자도 정상 접속이 되는지

```powershell
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.22 http://203.0.113.1/api/v1/health
```

`200`이 나와야 합니다. `203.0.113.1`은 pfSense의 WAN 주소이고, pfSense가 80번을 포털(`10.250.0.2:5000`)로 넘겨 줍니다.

### 2) 공격 ① 경계에서 막히는 신호: ping

```powershell
docker exec haedam-attacker ping -I 203.0.113.22 -c 1 -W 1 203.0.113.1
```

응답이 없어야 정상입니다(100% packet loss). pfSense가 WAN으로 들어온 ping을 기본 규칙으로 막고 그 기록을 Graylog로 보냅니다.

- **pfSense:** Status → System Logs → Firewall에 `203.0.113.22` 차단(빨간 X) 한 줄
- **Graylog Search:** `rule:"pfsense-block" AND src_ip:203.0.113.22`

### 3) 공격 ② 포털 스캔과 로그인 시도

입력 도구(원작 B)가 요청 3개를 보냅니다: 없는 경로 스캔(404) → 로그인 화면용 보안 토큰 받기(200) → 틀린 비밀번호로 로그인(401).

```powershell
docker cp tools/s8s10_input.py haedam-attacker:/lab/s8s10_input.py

docker exec haedam-attacker python /lab/s8s10_input.py --case S10 --run-id $run --out /tmp/$run.json --execute
docker exec haedam-attacker cat /tmp/$run.json
```

출력의 `"http"`에서 `status`가 `404`, `200`, `401` 순서인지 봅니다(`ping`도 한 번 더 보냄).

- **Graylog Search:** `src_ip:203.0.113.22` → `web-scan`(404), `login-bruteforce`(401) 이벤트

### 4) 탐지와 대응 (최대 1~2분 기다림)

Graylog는 1분마다 "15분 안에 같은 출발지에서 경계 차단·스캔·로그인 실패가 모두 나왔는가"를 확인합니다.

## S12 · 요청 폭주 (`203.0.113.42~46`, 가용성)

한 출발지가 포털에 요청을 몰아 보내는 경우입니다. 출발지를 포털에서 차단하면 그 출발지만 막히고 다른 시민은 그대로 씁니다. 회차마다 새 출발지(`.42`~`.46`)를 써서 티켓이 겹치지 않게 합니다.

### 1) 공격: 가벼운 요청 버스트

```powershell
docker exec haedam-attacker ip addr add 203.0.113.42/24 dev eth0   # 출발지 한 번만 추가
docker cp tools/s12_flood.py haedam-attacker:/lab/s12_flood.py
docker exec haedam-attacker python /lab/s12_flood.py --url http://203.0.113.1/api/v1/health --source 203.0.113.42 `
  --rates 4 --stage-seconds 60 --duration 70 --concurrency 3 --max-rate 10 --label s12-manual --out /tmp/s12.csv
```

`s12_flood.py`는 GET만 보내고 속도·시간 상한이 있으며, 출발지가 차단되면(403 비율이 높아지면) 스스로 멈춥니다. 4 req/s로 60초면 240건이라 60초 창에서 N=60을 넘깁니다. 끝에 `sent … blocked403 …` 요약이 나옵니다.

Graylog 정의: 같은 `src_ip`의 `web.request`가 60초 창에서 **N=60**(이 PC 한 대 실습값)을 넘으면 탐지합니다. 60초 창을 30초마다 평가합니다.

### 2) 효과

```powershell
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.42 http://203.0.113.1/api/v1/health   # 403
docker exec haedam-normal   curl -s -o /dev/null -w "%{http_code}`n" http://203.0.113.1/api/v1/health                          # 200
```

공격 출발지는 `403`(포털 `IP_BLOCKED`), 정상 시민은 `200`입니다. 볼 곳: Graylog Alerts의 `S12 요청 폭주`, n8n Executions의 `haedam-20`, 티켓 대시보드의 S12 티켓(조치 `portal block → applied`).

> **차단 기준을 요청 수로 바꾼 이유:** 팀 원본 haedam-20은 요청이 몰려도 포털 health 응답이 2초를 3회 연속 넘을 때만 차단합니다. PC 한 대에서는 부하를 올려도 health가 거의 안 느려져(수 ms) 차단 경로가 안 나옵니다. 그래서 탐지(요청 수 초과)가 뜨면 바로 차단하도록 `count_based`를 켰습니다. health 표본은 지우지 않고 사건 근거로 남깁니다.

### 3) 해제 (사람이 확인 후)

```powershell
$body = '{"seat":"D","case_id":"S12","group_key":"203.0.113.42","approver":"운영자","dry_run":false,"reason":"실습 원복"}'
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5678/webhook/haedam-release -ContentType 'application/json' -Headers @{ 'X-Haedam-Key' = $env:N8N_WEBHOOK_KEY } -Body $body
docker exec haedam-attacker curl -s -o /dev/null -w "%{http_code}`n" --interface 203.0.113.42 http://203.0.113.1/api/v1/health   # 200
```

`group_key`는 그 회차의 출발지입니다. 해제 뒤 공격 출발지는 다시 `200`, 티켓은 `restored`입니다. 같은 출발지를 다시 쓰려면 티켓이 겹치니 다음 `.43`을 씁니다.
