# S12 · 요청 폭주 (가용성, D · `203.0.113.42`)

한 출발지가 포털에 요청을 몰아 서비스를 느리게 만드는 상황입니다. 탐지는 **요청 수 기준**이고, 대응은 그 출발지만 포털에서 차단해 다른 시민은 그대로 쓰게 합니다.

> 이 저장소는 1회 성공까지만 확인했습니다(실측 3회·정량평가·검증 체크리스트는 아직). 팀 저장소도 보강 후 차단 경로를 관측한 회차가 없었습니다(health 기준이라 `no_action`으로 끝남). 이 PC에서는 차단 기준을 요청 수로 바꿔 차단 경로를 1회 확인했습니다.

## 탐지·대응

| 단계 | 내용 |
| --- | --- |
| 입력 | 공격 출발지(`.42`)에서 `/api/v1/health`로 가벼운 버스트(약 4 req/s) |
| 탐지 | Graylog `S12 요청 폭주 (src_ip 1분 요청 수)`: 같은 `src_ip`의 `web.request`가 60초 창에서 **N=60**을 넘으면 발동(이 PC 한 대 실습값). 60초 창·30초마다 평가 |
| 대응 | n8n `haedam-20` → 티켓 → `haedam-12` 포털 IP 차단. **요청 수 기준 차단**(`count_based`): 탐지가 곧 폭주 증거이므로 health 게이트 없이 차단하고, health 표본은 사용자 영향 근거로 함께 기록 |
| 효과 | 공격 출발지 `403`, 정상 시민(`.100`)은 `200` |
| 원복 | 사람이 확인 뒤 `haedam-50`으로 차단 해제 → 공격 출발지 다시 `200`, 티켓 `restored` |

## 팀 설계와 다른 점

팀 설계(haedam-20 원본)는 요청이 몰려도 포털 health 응답이 기준선(2000ms)을 3회 연속 넘을 때만 차단합니다. 팀 실측(1회, S12-20261103-LIVE01)은 health가 28~39ms라 `no_action`으로 끝났고 차단 경로를 관측하지 못했습니다. PC 한 대에서는 부하를 올려도 health가 거의 안 느려지므로, 탐지(요청 수 초과)가 뜨면 바로 차단하도록 `count_based`를 켰습니다. health 표본은 지우지 않고 사건 근거로 남깁니다.
