# S4 · 실패 뒤 성공 → 계정 잠금 (계정 탈취 의심, A · `203.0.113.11`)

비밀번호를 알아낸 공격자가 틀린 비밀번호를 몇 번 넣은 뒤 맞는 비밀번호로 로그인하는 상황입니다. 출발지를 막는 S1과 달리 **계정**을 잠그고 그 계정의 세션을 모두 회수합니다. 공격자가 이미 맞는 비밀번호를 알고 있으므로, 원복은 잠금 해제가 아니라 사람이 하는 **비밀번호 재설정**입니다.

## 탐지·대응

| 단계 | 내용 |
| --- | --- |
| 입력 | 계정 주인이 정상 출발지(`.100`)에서 가입 → 공격자(`.11`)가 틀린 비밀번호 5번 → 맞는 비밀번호로 로그인(200), 그 세션을 유지 |
| 탐지 | Graylog `S4 실패 뒤 성공 (username+src_ip)`: 10분 안 같은 `username`·`src_ip`의 로그인 실패(401)와 성공(200)이 모두 있고(`card(rule)>1`) 합계 6건 이상(`count()>5`). 429는 세지 않음. 1분마다 평가 |
| 대응 | n8n `haedam-31` → 티켓 → `haedam-13` 계정 잠금(대응 봇 111, 세션 회수). 실제 잠금은 `zz_` 시험 계정만 |
| 효과 | 공격자가 들고 있던 세션이 `401`로 끊김, 맞는 비밀번호로도 로그인 `401`, 다른 시민은 `200` |
| 원복 | 담당자가 비밀번호 재설정(`/response/accounts/<id>/reset`) → `haedam-50`이 티켓을 `restored`로 닫음 → 계정 주인이 새 비밀번호로 `200`, 공격자가 알던 옛 비밀번호는 `401` |

## 실행

```powershell
python lab/run_ticket.py S4 --restore     # 실측 1회, docs/tickets/S4/runs.jsonl에 추가
python lab/run_ticket.py S4 --baseline    # 정상 시민: 오타 3번 뒤 로그인 성공(4건) → 티켓 없어야 함
```

같은 출발지에서는 **5분 간격**을 둡니다. 한 회차가 `.11`에서 로그인을 8번쯤 하고, 포털은 출발지마다 5분에 20번까지만 받기 때문입니다(`LOGIN_RATE_LIMIT`). 넘으면 확인 요청이 401 대신 429를 받아 판정할 수 없습니다.

## 실측

"공격자"는 잠금 뒤 맞는 비밀번호로 다시 로그인한 결과(`401`이어야 함), "normal"은 정상 시민 접속, "해제 후 공격자"는 재설정 뒤 **계정 주인**의 새 비밀번호 로그인(`200`)입니다.

- 1~3회는 1분 간격으로 돌려 수정 전 회차로 센다. 3회차는 잠금·세션 회수·재설정까지 모두 됐지만, 마지막 "옛 비밀번호" 확인이 출발지 로그인 한도에 걸려 `429`가 나와 판정하지 못했다(`fail`). 간격을 5분으로 늘린 뒤 5~7회가 본 표 3/3이다.
- 세션 회수: 공격자가 쥔 세션은 매 회차 `401`로 끊겼다. 로그인 성공부터 회수까지 24.1·15.1·6.0초(수정 후).
- 기준선(4행): 정상 출발지에서 오타 3번 뒤 로그인 성공(4건, 조건 6건 미만) → 티켓 없음(오탐 0/1).
- 팀 값과 비교: 팀 S4-after-01(11/03, 1회)은 성공 입력부터 자동 잠금까지 6.975초였다(Graylog 처리 5.996초 + 탐지→잠금 0.979초). 이 PC의 입력→잠금은 6.4~24.1초, 중앙값 15.7초다. 차이는 대부분 Graylog의 1분 평가 주기 중 언제 입력했는지에서 오고, 탐지→잠금은 0.57~0.65초로 팀(0.979초)과 비슷하다.
